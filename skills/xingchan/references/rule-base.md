## 二、条目格式

```
{触发条件} → {偏好} → {边界} → {来源} → {置信度}
```

- **触发条件**：档位/领域/渠道/体裁组合，写清适用范围，用精确值描述
- **偏好**：可执行的操作指令，不是抽象态度
- **边界**：例外条件；无例外写“无”
- **来源**：日期 + 稿件名（可回指）+ **轨道标记【实战】/【架构】**（审查报告 P1 落刀 2026-08-23：来自稿件写作沉淀的标【实战】，来自系统架构迭代自举的标【架构】——E2 复盘的“规则库持续生长”硬指标只统计【实战】增量，防指标虚高）
- **置信度**：按 E 层 v2.0 **加权置信制**计分（真实退修 2 分／读者数据 1.5／评审-实战交叉命中 1／自我感觉 0.5，累计 ≥3 分=正式条目；速记口径仍称“≥3 次”；`1-2次`/低分=观察区）。跨会话计次用 conversation_search 查证

## 七、TDD 验证协议（规则库准入测试）

> 规则不是“写出来”的，是“验证出来”的。来源：obra/writing-skills —— TDD 应用于文档。

**核心原则**：每一条规则入库前，必须跑完 RED-GREEN-REFACTOR 循环。未经验证的规则只进观察区，不生效。

**RED 阶段（基线）**：不带规则跑一次压力场景，观察 Agent 是否犯规。如不犯规→规则不需要，放弃。如犯规→记录**精确的违约行为**和**Agent 的合理化借口**（原文）。

**GREEN 阶段（最小规则）**：写一条恰好阻止该违约行为的规则。重新跑同一场景，验证 Agent 遵守。如不遵守→规则太弱，回 RED 重写。

**REFACTOR 阶段（堵漏洞）**：压力场景注入新变异（换渠道/换档位/加时间压力），找 Agent 另辟蹊径的违约。发现→加反制→验证。封堵到连续 3 轮无新违约。

**准入签名**：每条正式条目末尾标注 `TDD验证: 202X-XX-XX | 基线违规数 | 最终轮次 | 反制数`。无 TDD 签名的条目，置信度自动降为“未验证”。
